Install and start BedrockPlus

Install the BedrockPlus command once, initialize one empty server folder, and use that same folder for every later start. BedrockPlus currently supports Python 3.13 and BDS 1.26.51.1.

1. Install the BedrockPlus command once

Open Command Prompt or PowerShell and install the public BedrockPlus package. This makes the bedrockplus command available on the computer.

pip install bedrockplus

2. First use: create a fresh server

Create or open an empty folder and run bedrockplus inside it. The folder must be empty except for a reusable Downloads cache.

mkdir MyBedrockPlusServer
cd MyBedrockPlusServer
bedrockplus
  1. 1
    Confirm the official BDS download

    Press Enter to accept Yes. BedrockPlus downloads the supported official server archive, or reuses a verified matching archive from Downloads.

  2. 2
    Let BedrockPlus prepare the folder

    It verifies the archive and creates server.properties, BedrockPlus.ini, plugins, logs, worlds, and private runtime data.

  3. 3
    Wait for the server to become ready

    The same command starts BDS with BedrockPlus and enabled plugins. Enter stop in the server console for a graceful shutdown.

Your files are protected

If the selected folder contains unrelated files, initialization stops with a warning and does not overwrite them.

3. Every later start

Return to the initialized server folder and run the same command. BedrockPlus uses the existing configuration, world, BDS installation, and plugins.

cd C:\Servers\MyBedrockPlusServer
bedrockplus

To install a plugin, stop the server, place its .bppack file or development folder in plugins beside server.properties, and start BedrockPlus again.

CommandPurpose
bedrockplusInitialize an empty folder when needed, then start the server.
bedrockplus initInitialize the current empty folder without starting BDS.
bedrockplus startStart an already initialized server.
bedrockplus doctorRun read-only checks when the server does not start correctly.
bedrockplus list-versionsShow the BDS versions supported by this BedrockPlus build.

From an empty folder to a running plugin

  1. 1
    Create the plugin

    Use the BedrockPlus command for Python, or start from the C++ example project.

  2. 2
    Write and test

    Implement lifecycle callbacks and register commands, listeners, and tasks when the server is ready.

  3. 3
    Build one package

    Run the pack command beside manifest.json. Python dependencies are prepared only during this explicit build.

  4. 4
    Install and start

    Copy the .bppack into plugins beside server.properties, then run bedrockplus in that server folder.

bedrockplus plugin python init "My First Plugin"
cd my-first-plugin
bedrockplus plugin pack
cmake -S . -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release
bedrockplus plugin pack package

Files and folders

The plugin creator owns the manifest and source. BedrockPlus creates integrity metadata and the finished archive. Server owners install only the .bppack file.

my-plugin/
├── manifest.json
├── requirements.txt        # optional, exact third-party versions
└── python/
    └── plugin.py
my-plugin/
├── CMakeLists.txt
├── src/
│   └── plugin.cpp
└── package/
    ├── manifest.json
    └── native/windows-x64/my_plugin.dll
One installed form

Do not install an unpacked folder and a .bppack with the same plugin ID together. BedrockPlus rejects duplicate identities.

Minimal typed plugin

The global switch changes every code sample on this page. Lifecycle registration and host calls remain explicit in both runtimes.

from bedrockplus import PluginHost

class MyFirstPlugin:
    id = "example.my-first-plugin"
    name = "My First Plugin"
    version = "0.1.0"

    def on_load(self, host: PluginHost) -> None:
        self.host = host

    def on_server_ready(self) -> None:
        self.host.log("info", "MY_PLUGIN.READY", "Plugin is ready")
#include <bedrockplus/sdk/plugin.hpp>

class MyFirstPlugin final : public bedrockplus::sdk::Plugin {
public:
    using Plugin::Plugin;
    void on_server_ready() override {
        logger().log(BP_LOG_INFO, "Plugin is ready", "MY_PLUGIN.READY");
    }
};

BEDROCKPLUS_PLUGIN(MyFirstPlugin, "example.my-first-plugin",
                   "My First Plugin", "0.1.0")

Python development and autocomplete

Install the public BedrockPlus package into the same Python environment selected by VS Code. The package contains typed interfaces and a py.typed marker, so Pylance can suggest classes, methods, fields, command shapes, and event types.

py -3.13 -m venv .venv
.venv\Scripts\activate
python -m pip install bedrockplus

In VS Code choose Python: Select Interpreter and select .venv. Imports such as from bedrockplus import PluginHost, Player, Server will then autocomplete.

C++20 development

Use Visual Studio 2022 with Desktop development with C++, CMake tools, and the Windows SDK. Link no private engine library: include the public headers and export the ABI v1 descriptor with BEDROCKPLUS_PLUGIN.

cmake -S . -B build -G "Visual Studio 17 2022" -A x64 \
  -DBEDROCKPLUS_ROOT=D:\path\to\BedrockPlusServerSoftware
cmake --build build --config Release
Runtime choice

Build with the static MSVC runtime so users do not need a separately installed redistributable. The full example CMake project already configures this.

Lifecycle callbacks

Load stores the host, enable prepares data, server ready registers runtime services, server stopping releases them, disable saves state, and unload performs final local cleanup. Never call the host after unload returns.

on_load · on_enable

Initialize plugin-owned state. Commands, events, and scheduling may not be ready yet.

on_server_ready · on_server_stopping

Register and explicitly release commands, listeners, and tasks while BDS runtime services are available.

on_disable · on_unload

Persist final state and release local resources. Exceptions must not cross the native ABI boundary.

Host API map

The same services are available through typed Python methods and C++ wrappers. Availability checks let a plugin fail clearly when it targets a newer host feature.

Plugin

Your entry class implements six lifecycle callbacks. The runtime constructs it once, passes the host during load, and calls server callbacks only while BDS services are usable.

MemberReturnsMeaning
on_load(host)None / bp_statusStore the host and create plugin-owned state. Runtime services may not be ready.
on_enable()None / bp_statusLoad configuration and prepare local resources.
on_server_ready()NoneRegister commands, events, and scheduled tasks here.
on_server_stopping()NoneUnregister runtime services and cancel tasks before BDS stops.
on_disable() · on_unload()NoneSave state, close local resources, and stop using the host after unload.
 
class MyPlugin:
    def on_load(self, host: PluginHost) -> None:
        self.host = host

    def on_server_ready(self) -> None:
        self.host.log("info", "MY.READY", "Runtime services are ready")
class MyPlugin final : public bedrockplus::sdk::Plugin {
public:
    using Plugin::Plugin;
    void on_server_ready() override {
        logger().info("Runtime services are ready");
    }
};

PluginHost Python

BedrockPlus supplies this object to on_load. Do not construct it yourself. Boolean results report whether a request was accepted; command acceptance does not prove that BDS completed the command.

MethodReturnsMeaning
log(level, event_code, message, fields=None)NoneWrite a structured plugin log record. Field keys and values are strings.
data_directory()strReturn this plugin's private persistent directory.
scheduler_available() · events_available() · commands_available()boolCheck whether a service exists before using an optional host feature.
schedule(...) · cancel_task(id)int · boolCreate or cancel server-thread work. Keep the returned task ID.
subscribe_event(...) · unsubscribe_event(id)int · boolAttach or remove an event listener. Keep the returned subscription ID.
register_command(...) · unregister_command(name)None · boolAdd a typed native slash command or remove it.
dispatch_server_command(command)boolQueue one command as the server. Do not include a leading slash or newline.

from pathlib import Path

data_file = Path(self.host.data_directory()) / "state.json"
accepted = self.host.dispatch_server_command("say Hello from plugin")
// C++ exposes focused wrappers instead of PluginHost directly.
auto data_file = data_directory() / "state.json";
bool accepted = commands().dispatch_server_command("say Hello from plugin");

Logger · Scheduler · Events · Commands

These protected Plugin accessors return non-owning wrappers around the host ABI. Call available() when a plugin may run on different API revisions, and retain task or subscription IDs for cleanup.

if (events().available()) {
    join_subscription_ = events().subscribe("player.join", on_join);
}
logger().log(BP_LOG_INFO, "Loaded", "MY.LOAD", {{"mode", "safe"}});

Typed objects and connection snapshots

Objects copy stable data instead of exposing raw BDS pointers. Missing optional values mean the active BDS profile did not provide them; BedrockPlus never invents connection data.

Server(host)

A convenient object factory and safe command façade. Create one after receiving PluginHost and keep it on your plugin.

ConnectionInfo · SocketAddress

ConnectionInfo contains address, ping, device, input, version, locale, and optional client FPS snapshots. SocketAddress separates host and port. Treat every value as optional operational data, not a permanent identity.

Properties: address, ping_ms, device_id, device_model, device_os, input_mode, game_version, locale, client_fps; host, port.

connection = player.connection
if connection and connection.address:
    host = connection.address.host
    port = connection.address.port
if (player.connection && player.connection->address) {
    const auto& host = player.connection->address->host;
    auto port = player.connection->address->port;
}

Vector3 · Location · Level/LevelSnapshot

Vector3 stores x, y, and z coordinates. Location adds level name, dimension identifier, yaw, and pitch. Level identifies a level and dimension but does not load chunks or change the world.

Properties: x, y, z; level_name, dimension_id, position, yaw, pitch; name.

position = Vector3(12.5, 64.0, -8.0)
place = Location("BedrockPlus", "minecraft:overworld", position, yaw=90.0)
level = self.server.level(place.level_name, place.dimension_id)
Location place{"BedrockPlus", "minecraft:overworld",
               Vector3{12.5, 64.0, -8.0}, 90.0F, 0.0F};
LevelSnapshot level{place.level_name, place.dimension_id};

Entity/EntitySnapshot · ItemStack

Entity stores a runtime ID, type ID, and optional location. ItemStack stores type ID, amount, auxiliary value, and custom name. In API v1 these are descriptive values: constructing one does not spawn an entity or edit inventory.

Properties: runtime_id, type_id, location; amount, aux_value, custom_name.

zombie = self.server.entity(42, "minecraft:zombie", place)
reward = ItemStack("minecraft:diamond", amount=2, custom_name="Prize")
EntitySnapshot zombie{42, "minecraft:zombie", place};
ItemStack reward{"minecraft:diamond", 2, 0, "Prize"};
Handle connection identifiers carefully

IP addresses and device identifiers may be operationally useful, but plugins should collect, log, and retain only what the server owner genuinely needs.

Typed slash commands and vanilla control

Registered commands join the native BDS command registry, including chat autocomplete. Overloads support integer, real, string, remaining text, and enum arguments. Enum choices provide literal suggestions.

host.register_command(
    "weatherplus", callback,
    description="Weather controls",
    aliases=["wp"],
    overloads=[[{
        "name": "action", "type": "enum",
        "choices": ["start", "stop", "status"]
    }, {"name": "seconds", "type": "int", "optional": True}]],
)
CommandDefinition command{
    "weatherplus", "Weather controls", "any", {"wp"},
    {CommandOverload{{
        {"action", CommandArgumentType::enumeration, false,
         {"start", "stop", "status"}},
        {"seconds", CommandArgumentType::integer, true, {}}
    }}}
};
commands().register_command(command, callback);

Player and server command events run before BDS executes vanilla or BedrockPlus commands. A listener may cancel execution or replace the command string. Hidden vanilla commands disappear from player suggestions and are rejected when typed, while the server console remains unaffected.

Events, priority, cancellation, and mutation

Subscribe after server ready and keep the returned ID for cleanup. Priorities run from earliest to monitor. Monitor listeners should observe rather than modify.

subscription = host.subscribe_event(
    "player.command", on_command, priority=-100
)

def on_command(event: Event) -> None:
    if event["fields"]["command"] == "blocked":
        event["cancelled"] = True
auto subscription = events().subscribe(
    "player.command", [](const Event& event) {
        if (event.field("command") == "blocked") {
            static_cast<void>(event.cancel());
        }
    }, EventPriority::early);

Server-thread scheduler

Schedule one-shot or finite repeating callbacks in milliseconds. Keep task IDs and cancel outstanding work during server stopping. A plugin instance accepts at most 1024 submitted callbacks in API v1.

once = host.schedule(callback, delay_ms=1000)
repeat = host.schedule(callback, delay_ms=2000,
                       interval_ms=2000, runs=3)
host.cancel_task(repeat)
auto once = scheduler().schedule(callback, 1'000);
auto repeat = scheduler().schedule(callback, 2'000, 2'000, 3);
scheduler().cancel(repeat);

Structured logs and private data

Log levels, stable event codes, and string fields appear in console and dated files according to BedrockPlus.ini. Each plugin receives a private persistent directory under the hidden BedrockPlus state path.

from pathlib import Path

host.log("info", "MY_PLUGIN.READY", "Ready", {"mode": "safe"})
state_file = Path(host.data_directory()) / "state.json"
logger().log(BP_LOG_INFO, "Ready", "MY_PLUGIN.READY",
             {{"mode", "safe"}});
auto state_file = data_directory() / "state.json";

Plugin text may use ampersand color codes such as &a; BedrockPlus converts supported codes to the Minecraft section-sign format before dispatch.

Self-contained dependencies

Put direct, exact versions in requirements.txt, one package per line. An optional requirements.lock takes priority and should contain the complete tested set. bedrockplus plugin pack installs them into python/vendor inside a temporary staging copy; server startup never runs pip.

# requirements.txt
TikTokLive==6.6.5

Prefer static runtime and library linkage or ship explicitly licensed DLL dependencies inside native/windows-x64. The plugin must not rely on the developer machine's PATH or debug runtime.

Review what you ship

Dependencies execute with the same operating-system access as the server. Pin versions, keep required notices, and rebuild after security updates.

Build, validate, and install

Run the command in the folder containing manifest.json. It validates paths, identity, runtime metadata, and generated hashes, then writes the finished archive beside the manifest unless an output path is supplied.

bedrockplus plugin pack
bedrockplus plugin pack . -Output my-plugin.bppack

Copy the unchanged result into the server's plugins directory. Do not unzip it and do not rename internal files after building.

Unpacked development plugins

During development, a plugin may remain as a normal folder directly under plugins. Python vendor dependencies work in either form. Use .bppack for repeatable installation, transfer, and release.

Bundled vanilla packs

A .bppack may include behavior_packs and resource_packs directories. BedrockPlus validates them and manages their world installation without changing the original plugin archive.

Validation and common failures

Plugin does not load

Read the first validation error in console and logs. Check manifest paths, API version, runtime version, duplicate IDs, and package integrity.

Event callback never runs

Verify that the event is one of the five live feeds in the table above and that subscription occurs during server ready.

Python import fails

Declare the exact package in requirements.txt and rebuild. Do not install dependencies globally and do not run pip during server startup.

Command lacks autocomplete

Register typed overloads after server ready. Use enum choices for fixed words such as connect, disconnect, and status.

Current preview boundaries

  • The runtime currently targets 64-bit Windows, BDS 1.26.51.1, Python 3.13, and C++ ABI v1.
  • Python plugins share one embedded interpreter. Dependency folders are isolated, but this is not process-level security isolation.
  • Only server.tick, player.join, player.quit, player.command, and server.command have native producers today.
  • Plugins must target the documented BedrockPlus API. Existing compiled plugins from another host are not binary-compatible.
  • C++ gameplay objects are copied snapshots in API v1; behavioral Player and Server wrappers currently exist only in Python.
