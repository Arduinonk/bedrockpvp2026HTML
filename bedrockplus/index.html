Install and start BedrockPlus

Install the BedrockPlus command once, initialize one empty server folder, and use that same folder for every later start. BedrockPlus currently supports Python 3.13 and BDS 1.26.51.1.

1. Install the BedrockPlus command once

Open Command Prompt or PowerShell and install the public BedrockPlus package. This makes the bedrockplus command available on the computer.

pip install bedrockplus

2. First use: create a fresh server

Create or open an empty folder and run bedrockplus inside it. The folder must be empty except for a reusable Downloads cache.

mkdir MyBedrockPlusServer
cd MyBedrockPlusServer
bedrockplus
  1. 1
    Confirm the official BDS download

    Press Enter to accept Yes. BedrockPlus downloads the supported official server archive, or reuses a verified matching archive from Downloads.

  2. 2
    Let BedrockPlus prepare the folder

    It verifies the archive and creates server.properties, BedrockPlus.ini, plugins, logs, worlds, and private runtime data.

  3. 3
    Wait for the server to become ready

    The same command starts BDS with BedrockPlus and enabled plugins. Enter stop in the server console for a graceful shutdown.

Your files are protected

If the selected folder contains unrelated files, initialization stops with a warning and does not overwrite them.

3. Every later start

Return to the initialized server folder and run the same command. BedrockPlus uses the existing configuration, world, BDS installation, and plugins.

cd C:\Servers\MyBedrockPlusServer
bedrockplus

To install a plugin, stop the server, place its .bppack file or development folder in plugins beside server.properties, and start BedrockPlus again.

CommandPurpose
bedrockplusInitialize an empty folder when needed, then start the server.
bedrockplus initInitialize the current empty folder without starting BDS.
bedrockplus adoptInstall missing BedrockPlus/BDS files into an existing server folder without overwriting worlds, plugins, packs, or operator configuration.

From an empty folder to a running plugin

  1. 1
    Create the plugin

    Use the BedrockPlus command for Python, or start from the C++ example project.

  2. 2
    Write and test

    Implement lifecycle callbacks and register commands, listeners, and tasks when the server is ready.

  3. 3
    Build one package

    Run the pack command beside manifest.json. Python dependencies are prepared only during this explicit build.

  4. 4
    Install and start

    Copy the .bppack into plugins beside server.properties, then run bedrockplus in that server folder.

One installed form

Do not install an unpacked folder and a .bppack with the same plugin ID together. BedrockPlus rejects duplicate identities.

Minimal typed plugin

The global switch changes every code sample on this page. Lifecycle registration and host calls remain explicit in both runtimes.

from bedrockplus import PluginHost

class MyFirstPlugin:
    id = "example.my-first-plugin"
    name = "My First Plugin"
    version = "0.1.0"

    def on_load(self, host: PluginHost) -> None:
        self.host = host

    def on_server_ready(self) -> None:
        self.host.log("&aPlugin is ready")
#include <bedrockplus/sdk/plugin.hpp>

class MyFirstPlugin final : public bedrockplus::sdk::Plugin {
public:
    using Plugin::Plugin;
    void on_server_ready() override {
        logger().log(BP_LOG_INFO, "Plugin is ready", "MY_PLUGIN.READY");
    }
};

BEDROCKPLUS_PLUGIN(MyFirstPlugin, "example.my-first-plugin",
                   "My First Plugin", "0.1.0")

Lifecycle callbacks

Load stores the host, enable prepares data, server ready registers runtime services, server stopping releases them, disable saves state, and unload performs final local cleanup. Never call the host after unload returns.

on_load(host) · on_enable()

Initialize plugin-owned state. Commands, events, and scheduling may not be ready yet.

on_server_ready() · on_server_stopping()

Register and explicitly release commands, listeners, and tasks while BDS runtime services are available.

on_disable() · on_unload()

Persist final state and release local resources. Exceptions must not cross the native ABI boundary.

Host API map

The same services are available through typed Python methods and C++ wrappers. Availability checks let a plugin fail clearly when it targets a newer host feature.

Plugin

Your entry class implements six lifecycle callbacks. The runtime constructs it once, passes the host during load, and calls server callbacks only while BDS services are usable.

MemberReturnsMeaning
on_load(host)None / bp_statusStore the host and create plugin-owned state. Runtime services may not be ready.

on_server_stopping()NoneUnregister runtime services and cancel tasks before BDS stops.

Vector3 · Location · Level/LevelSnapshot

Vector3 stores x, y, and z coordinates. Location adds an optional level name and dimension identifier. Python Level can filter verified native entities for vanilla dimensions; BlockSource, chunks and native block mutation are not public yet.

Properties: x, y, z, level_name, dimension_id, position, yaw, pitch; Level.entities, native_dimension_id.

Native boss-bar API

Create plugin-owned bars, attach authenticated players, and update the visible title, progress, color, style, and visibility through native BDS packets. No vanilla command or fake entity is used.

BossBar · BossBarColor · BossBarStyle

Connect a boss bar to a player

Create the Server facade during load, subscribe to player.join when the server is ready, defer attachment until the next tick, retain the returned BossBar, and destroy it when the player leaves or the plugin stops.

  1. 1
    Create

    Call Server.create_boss_bar with a title, color, style, progress from 0.0 to 1.0, and visibility.

  2. 2
    Attach

    Call add_player with a currently authenticated Player. Creating a bar alone does not show it to anybody.

  3. 3
    Retain and update

    Keep the BossBar object in plugin state, then call set_title, set_progress, set_color, set_style, show, or hide.

  4. 4
    Destroy

    Call destroy when the viewer leaves or during server stopping so the native bar and retained state are released.

# Create once in on_load:
self.server = Server(self.host)
self.bars = {}

# Attach on the next tick after player.join:
def attach() -> None:
    player = self.server.get_player(event.player.session_id)
    if player is None:
        return
    bar = self.server.create_boss_bar(
        "Welcome!", color=BossBarColor.PURPLE,
        style=BossBarStyle.SOLID, progress=1.0,
    )
    bar.add_player(player)
    self.bars[player.session_id] = bar

self.host.schedule(attach)

# On player.quit or on_server_stopping:
bar = self.bars.pop(event.player.session_id, None)
if bar is not None:
    bar.destroy()
// Defer this fragment from PlayerJoinEvent to the next tick:
scheduler().run([this, session = event.player().session_id] {
    auto player = server().get_player(session);
    if (!player) return;
    auto bar = server().create_boss_bar(
        "Welcome!", 1.0F,
        BossBarColor::purple, BossBarStyle::solid);
    bar.add_player(*player);
    bars_.insert_or_assign(session, std::move(bar));
});

// On quit or stopping:
if (auto found = bars_.find(session); found != bars_.end()) {
    found->second.destroy();
    bars_.erase(found);
}
Why the next tick?

player.join is delivered inside the completed native spawn path. Reading the Player is safe immediately; client-facing UI work is deferred to avoid re-entering BDS during spawn.

How to subscribe to an event

A subscription connects one exact event name to one callback method. Register it in on_server_ready, keep the numeric subscription ID, and unsubscribe during on_server_stopping.

PartWhat you provide
"player.join"The exact canonical event name from the live-events table.
self.on_player_joinA function reference, without parentheses. BedrockPlus calls it later and supplies the typed event object.
EventPriority.NORMALOptional listener order. NORMAL is appropriate unless the plugin specifically needs earlier or monitor behavior.
subscription_idThe integer returned by subscribe_event. Store it so the exact listener can be removed.
event.playerThe typed Player associated with PlayerJoinEvent; read its documented properties directly.
from bedrockplus import EventPriority, PlayerJoinEvent

# In on_server_ready: save the returned ID.
self.join_subscription = self.host.subscribe_event(
    "player.join",          # exact event name
    self.on_player_join,     # function reference; do not add ()
    EventPriority.NORMAL,
)

# BedrockPlus calls this method and supplies the event.
def on_player_join(self, event: PlayerJoinEvent) -> None:
    player = event.player
    self.host.log(
        f"{player.display_name} joined; XUID={player.xuid or 'unavailable'}"
    )

# In on_server_stopping: remove the exact subscription.
self.host.unsubscribe_event(self.join_subscription)
// In on_server_ready: save the returned ID.
join_subscription_ = events().subscribe<PlayerJoinEvent>(
    [this](const PlayerJoinEvent& event) {
        const auto player = event.player();
        logger().log(
            BP_LOG_INFO, player.name + " joined", "PLAYER_INFO.JOIN",
            {{"session", player.session_id}, {"xuid", player.xuid}});
    },
    EventPriority::normal);

// In on_server_stopping:
events().unsubscribe(join_subscription_);
Correct lifecycle location

on_load only stores PluginHost. Runtime services become usable in on_server_ready. Remove listeners in on_server_stopping before plugin code is disabled and unloaded.

player.join is observational

It cannot be cancelled. Reading identity and connection snapshots is immediate; defer messages, boss bars, or other client-facing actions to the next tick.

Player and server command events run before BDS executes vanilla or BedrockPlus commands. A listener may cancel execution or replace the command string. Hidden vanilla commands disappear from player suggestions and are rejected when typed, while the server console remains unaffected.

Events, priority, cancellation, and mutation

Subscribe after server ready and keep the returned ID for cleanup. Priorities run from earliest to monitor. Monitor listeners should observe rather than modify.

        event.cancel()

Moderate real entity attacks

Subscribe to player.attack for authenticated ItemUseOnActor attack attempts. Air swings and block actions are different signals. Count the event even when cancelled, and combine CPS with context before taking moderation action.

from bedrockplus import PlayerAttackEvent

self.attack_subscription = self.host.subscribe_event(
    "player.attack", self.on_player_attack
)

def on_player_attack(self, event: PlayerAttackEvent) -> None:
    self.host.log(
        f"{event.player.name} attacked {event.target_runtime_id}; "
        f"CPS={event.cps}"
    )
    if event.cps > 18:
        event.cancel()
attack_subscription_ = events().subscribe<PlayerAttackEvent>(
    [this](const PlayerAttackEvent& event) {
        const auto cps = event.clicks_per_second().value_or(0);
        logger().info("Attack CPS=" + std::to_string(cps));
        if (cps > 18) {
            static_cast<void>(event.cancel());
        }
    });
Attempt, not confirmed damage

The event proves that the authenticated client submitted a targeted attack which reached BDS validation. It does not claim that armor, invulnerability, reach, game rules, or later combat logic allowed damage.

Plugin output and private data

Use log, debug, warn, error, or critical like print: pass the values, and the method selects the timestamped level and console color. Plain print writes Minecraft-colored console text without a timestamp. Each plugin also receives a private persistent data directory.

from pathlib import Path

host.log("&aReady")
host.warn("Configuration is incomplete")
host.error("Could not load file:", filename)
print("&bThis line has no timestamp")
state_file = Path(host.data_directory()) / "state.json"
logger().log(BP_LOG_INFO, "Ready", "MY_PLUGIN.READY",
             {{"mode", "safe"}});
auto state_file = data_directory() / "state.json";

Python print inside a plugin is plugin-local BedrockPlus output: it supports ampersand color codes such as &a and bypasses the timestamp. Use host.log/warn/error when the line should also be retained in plugin log files.

Self-contained dependencies

Put direct, exact versions in requirements.txt, one package per line. An optional requirements.lock takes priority and should contain the complete tested set. bedrockplus plugin pack installs them into python/vendor inside a temporary staging copy; server startup never runs pip.

# requirements.txt
TikTokLive==6.6.5

Prefer static runtime and library linkage or ship explicitly licensed DLL dependencies inside native/windows-x64. The plugin must not rely on the developer machine's PATH or debug runtime.

Review what you ship

Dependencies execute with the same operating-system access as the server. Pin versions, keep required notices, and rebuild after security updates.

Build, validate, and install

Run the command in the folder containing manifest.json. It validates paths, identity, runtime metadata, and generated hashes, then writes the finished archive beside the manifest unless an output path is supplied.

bedrockplus plugin pack
bedrockplus plugin pack . -Output my-plugin.bppack

Copy the unchanged result into the server's plugins directory. Do not unzip it and do not rename internal files after building.

Unpacked development plugins

During development, a plugin may remain as a normal folder directly under plugins. Python vendor dependencies work in either form. Use .bppack for repeatable installation, transfer, and release.

Automatic development-pack activation

Before BDS starts, BedrockPlus reads valid folders, .zip files, and .mcpack files from development_behavior_packs and development_resource_packs, then updates the active world's registration JSON. The pack files themselves are not moved, extracted, or added to .bppack.

  • Changing a pack manifest version updates the matching world registration on the next start.
  • A folder, archive, or manifest header name ending in Disabled is excluded from BedrockPlus-managed registrations.
  • Registrations not owned by BedrockPlus are preserved, so server owners remain free to manage normal world packs themselves.

Validation and common failures

Plugin does not load

Read the first validation error in console and logs. Check manifest paths, API version, runtime version, duplicate IDs, and package integrity.

Event callback never runs

Verify the exact event name in the live table and subscribe during server ready. A listener that raises an exception is logged and removed for safety.

Python import fails

Declare the exact package in requirements.txt and rebuild. Do not install dependencies globally and do not run pip during server startup.

Command lacks autocomplete

Register typed overloads after server ready. Use enum choices for fixed words such as connect, disconnect, and status.

Current Beta 8 boundaries

  • The runtime currently targets 64-bit Windows, BDS 1.26.51.1, Python 3.13, and C++ ABI v1.
  • Python plugins share one embedded interpreter. Dependency folders are isolated, but this is not process-level security isolation.
  • The nineteen documented event types, read-only Entity fields, native item registry, and native scoreboard are live; native Entity mutation, Level/BlockSource, chunks, inventory, NBT, forms, and raw packets remain future milestones.
  • Plugins must target the documented BedrockPlus API. Existing compiled plugins from another host are not binary-compatible.
  • Player identity/connection and Entity data are pointer-free copied snapshots. Existing Player convenience actions are explicit command-backed operations and are not presented as completed native object methods.
